# 실험 — 실제 저장소에 형식 적용해보기

Last Updated: 2026-08-27

로드맵 M0의 마지막 항목: "실제 저장소 3개로 매니페스트를 손으로 작성해보기 — 형식이 현실에 맞는지 확인하는 유일한 방법".

**직접 해보시려면 [RUNBOOK.md](RUNBOOK.md)** — 저장소 하나에 대해 처음부터 끝까지 20분.

| 저장소 | 형태 | 상태 |
| :--- | :--- | :--- |
| [context-compress](context-compress/AGENT_GUIDE.md) | npm CLI + MCP 서버 + 훅. 문서가 거의 전부 README 안에 있음 | 초안 완료, 참조 25건 검증 통과 |
| [open-agent-contribution](open-agent-contribution/AGENT_GUIDE.md) | GitHub Action + CLI. `docs/`와 `examples/` 보유 | 완료. Docs 16 · flow 5 · Task 3, 참조 65건 전부 해석 |
| [cmux](cmux/AGENT_GUIDE.md) | 네이티브 앱. `docs/` 40개 이상, `AGENTS.md` 기존재 | 완료. Docs 12 · flow 4 · Task 1, 경로 12건 전부 해석 |

세 저장소 중 둘은 **저작 프로토콜만 건네받은 에이전트**가 작성했습니다. 사람의 개입 없이 형식이 성립하는지가 이 두 건의 핵심 검증 항목이었고, 성립했습니다. 대신 프로토콜의 결함 세 가지가 드러났습니다(발견 8~10).

## context-compress 결과

[저작 프로토콜](../.context/architecture/authoring-protocol.md)을 그대로 따라 작성했습니다. 산출물: [`context-compress/AGENT_GUIDE.md`](context-compress/AGENT_GUIDE.md) — Docs 12개, Code map 10개, flow 4개, Task 2개.

A6 자가 검증: 파일·디렉터리 15건 + README 앵커 10건 = **참조 25건 전부 해석됨**.

### 발견 1 — README가 곧 문서 전부인 경우가 예외가 아니라 기본이다

`docs/`에는 벤치마크 리포트 세 개뿐이고, 실제 진입점 12개 중 **9개가 README 앵커**였습니다. `path`에 프래그먼트를 허용해둔 덕에 형식은 버텼습니다.

```
| quickstart | README.md#quickstart | install, setup, `setup --auto`, first run | S |
```

→ **규격 반영 완료**: 저작 프로토콜에서 이 경우를 "함정" 표의 한 줄이 아니라 **기본 경로**로 올려야 합니다. 대부분의 저장소가 이렇습니다.

### 발견 2 — CHANGELOG가 FAQ의 최고 광맥이다

troubleshoot flow의 FAQ 6줄 중 4줄이 `CHANGELOG.md`의 수정 목록에서 거의 그대로 나왔습니다.

- `doctor`는 통과라는데 재시작하면 인덱스가 비어 있다
- `fetch_and_index`가 맨 `HTTP 403`으로 실패한다
- 환경변수를 명령 앞에 붙였는데 안 먹는다

잘 쓴 CHANGELOG는 **"사람들이 여기서 막혔다"를 이미 문장으로 적어놓은 문서**입니다. 이슈 라벨보다 접근성도 좋습니다.

→ **규격 반영 완료**: A2의 출처 우선순위에서 CHANGELOG를 3위 → 2위로 올립니다.

### 발견 3 — "증거 없으면 flow를 만들지 않는다" 규칙이 실제로 작동했다

최신 릴리스 2026.8.0은 hardening 릴리스라 breaking change가 없습니다. 규칙에 따라 `upgrade` flow를 **만들지 않았습니다**. 규칙이 없었다면 빈 껍데기 flow가 하나 생겼을 겁니다.

### 발견 4 — A7(사람에게 묻기)은 우회할 수 없다

`Not for`와 `status`는 저장소를 아무리 읽어도 나오지 않았습니다. README는 자기가 못 하는 일을 쓰지 않습니다. 초안에는 채워 넣되 HTML 주석으로 표시했습니다.

```html
<!-- TODO(maintainer): the overview below, the Not for line, and status in the
     frontmatter cannot be derived from the repo. Confirm them and delete this. -->
```

→ **규격 반영 완료**: 이 주석 형태를 `<!-- TODO(maintainer): ... -->`로 표준화하고, `validate`가 남아 있으면 경고하도록 합니다. 현재 규격에는 "확인 필요"를 표시하는 방법이 없습니다.

### 발견 5 — 프로토콜의 가치가 작성 도중에 실증됐다

이 파일을 heredoc으로 쓰려다 context-compress의 PreToolUse 훅에 차단당했습니다. FAQ 본문에 다운로드 도구 이름이 들어 있었기 때문입니다. **CHANGELOG에 "heredoc 본문을 명령으로 읽던 버그"로 기록된 바로 그 증상**입니다.

이 매니페스트를 가진 에이전트라면 같은 증상에서 한 번에 `hook`·`changelog` 두 문서로 갔을 겁니다. 저는 그러지 못하고 우회 방법을 직접 찾았습니다.

### 발견 6 — 프롬프트가 과도하게 규정적이면 에이전트가 답을 포기한다

1차 세션 실패. ORIENT는 여섯 항목 전부 통과했으나, 첫 질문(`rtk랑 뭐가 다른가요`)에서 이렇게 답했습니다.

> 로컬에 문서가 없습니다. 다음 단계를 택일해 주세요.
> 1) 원격에서 가져오기 — 외부 요청이므로 동의가 필요합니다
> 2) 이슈로 에스컬레이션

매니페스트 frontmatter에 `base`가 원격 URL로 **이미 선언돼 있는데도** 동의를 물었습니다. 메인테이너가 승인해둔 경로입니다. 규칙을 지키느라 답을 못 준 셈입니다.

원인은 규칙의 내용이 아니라 **적용 범위**였습니다.

| 초안 프롬프트의 문제 | 고친 방향 |
| :--- | :--- |
| "다른 파일 열지 마라"를 세션 전체에 걸었다 | **첫 응답까지만** 적용한다고 명시 |
| "추측하지 마라"가 도움 자체를 막았다 | 추론은 허용하되 **출처를 구분해 표시** |
| 문서를 못 찾으면 사용자에게 선택지를 떠넘겼다 | **폴백 사다리** + "막다른 길 금지" 명시 |
| 금지 목록만 있고 목표가 없었다 | 맨 앞에 **"지도이지 울타리가 아니다"** 한 줄 |

→ **규격 반영 완료**:
- §4.9 **경로 해석** 신설 — 저장소 루트 → `base` 원격 → 파일명 검색 → `escalate_to`. `base`는 선언된 경로이므로 별도 동의 없이 쓴다(SHOULD). 1단계 실패로 멈추는 것을 MUST NOT으로 금지.
- §5.3 규칙 4를 **교정(calibration) 규칙**으로 교체. "추측 금지"(MUST NOT) → "답하되 근거의 출처를 구분해 표시"(MUST). **금지되는 것은 추론이 아니라 근거 없는 단정**이다.
- 초기 프롬프트 정본 전면 개정 → [`reference/readme-block.md`](../.context/reference/readme-block.md)

부수적으로 실험 설정도 틀렸습니다 — `experiments/` 디렉터리에서 실행해 `README.md`가 없었습니다. 다만 유연한 에이전트라면 `base`로 넘어가 답했어야 하므로, 이건 원인이 아니라 방아쇠였습니다. 매니페스트는 저장소 루트에 두고 거기서 실행하는 것으로 절차를 고쳤습니다.

### 발견 7 — 발견 순서가 현실과 반대였다

2차 세션. 템플릿의 `<org>/<repo>`를 치환하지 않은 채, 저장소도 아닌 `experiments/` 디렉터리에서 실행했습니다. 에이전트의 첫 줄:

> the raw URL still has literal `<org>/<repo>` placeholders, so I went straight to the local file

치환 안 된 URL을 **스스로 알아채고** 로컬로 넘어가 첫 응답을 정상 수행했습니다. 묻지도 멈추지도 않았습니다. 발견 6번의 수정이 의도대로 작동한 것입니다 — 같은 조건에서 1차는 선택지를 떠넘기고 멈췄습니다.

**규칙을 더 붙일 필요는 없다는 것이 이 실험의 결론입니다.** 다만 다른 문제가 드러났습니다.

초안은 **원격 URL을 먼저** 읽게 했습니다. 실제 사용 맥락을 세어보면 순서가 반대입니다.

| 맥락 | 로컬 | 원격 |
| :--- | :-: | :-: |
| 저장소를 클론하고 CLI 에이전트를 띄운 사용자 | ○ | 불필요한 왕복 |
| 저장소의 하위 디렉터리에서 실행한 사용자 | ○ (루트 폴백) | 불필요한 왕복 |
| ChatGPT 웹 등 저장소가 없는 사용자 | ✗ | ○ |

로컬이 두 맥락을 덮고, 원격은 하나뿐입니다. 게다가 원격을 먼저 두면 **치환을 잊었을 때 첫 시도가 반드시 실패**합니다.

→ **템플릿 반영 완료**: `Read <URL>` → `Find this project's AGENT_GUIDE.md — ./ → repo root → <URL>`. 이름 기반 발견으로 바꾸면서 문장이 오히려 짧아졌습니다.

치환 누락 자체는 프롬프트가 아니라 도구가 막습니다. `validate`가 README에 `<org>`가 남아 있으면 오류로 처리합니다(M2).

## open-agent-contribution · cmux 결과

두 매니페스트는 저작 프로토콜과 형식 치트시트만 읽은 에이전트가 작성했습니다.

| | OAC | cmux |
| :--- | :--- | :--- |
| Docs | 16 | 12 (`docs/` 전체 40+ 중) |
| flow | 5 | 4 |
| Task | 3 | 1 |
| A6 검증 | 참조 65건 전부 해석 | 경로 12건 전부 해석 |

**cmux의 진입점 선별은 통과했습니다.** 40개 넘는 문서에서 12개를 골랐고, 기존 `AGENTS.md`를 Docs 표에 넣되 내용을 복제하지 않고 기여 flow에서 넘겨줬습니다. "8~12개로 자른다"는 지침이 실제로 작동했습니다.

**OAC는 `upgrade` flow를 만들었습니다.** CHANGELOG에 breaking이라고 명시된 절은 없지만, CalVer 오기로 인한 버전 롤백과 패키지명 변경(`@open330/oac-core` → `@open330/oac`)이 실질적 breaking이라고 판단했습니다. FAQ 4줄이 나왔으니 껍데기가 아닙니다. 발견 3번의 규칙이 기계적 판정이 아니라 판단으로 작동한 사례입니다.

### 발견 8 — 백틱이 과부하됐다 ★

FAQ 한 줄에서 `` `foo` ``는 **id 참조이기도 하고 평범한 코드 서식이기도** 합니다. 검증기가 사용자 문구 속 `--retry-failed`를 깨진 id로 잡아냈고, 작성 에이전트는 **질문 문구를 훼손해서** 파서를 만족시켜야 했습니다.

> a rule that made the manifest worse

규칙이 산출물을 나쁘게 만들었다면 규칙이 틀린 겁니다.

→ **규격 반영 완료**: 위치 규칙으로 해소합니다. **`→` 앞의 백틱은 평범한 코드 서식이고, id 참조는 `→`·`→ task`·`→ flow` 뒤에만 온다.** 이미 실질적으로 그렇게 쓰이고 있으므로 명시만 하면 됩니다.

### 발견 9 — flow 목록이 닫힌 집합으로 읽혔다 ★

OAC에는 청중이 둘입니다. OAC를 **돌리는 사람**과, 에이전트가 쓴 PR을 **받는 타겟 저장소 메인테이너**. 후자는 onboard/upgrade/troubleshoot/integrate/contribute 어디에도 안 들어갑니다. 에이전트는 이를 `Audiences` 한 줄로 욱여넣었고, 스스로 "under-serves it"이라고 평가했습니다.

> The fixed five-flow list is the format's biggest limitation.

→ **규격 반영 완료**: 다섯 종은 **예시이지 열거가 아닙니다.** flow id는 자유이고, A4의 표는 "증거가 있으면 만들라"는 흔한 사례 목록일 뿐임을 명시합니다. 위 OAC 사례라면 `receive`(PR을 받는 쪽) 같은 flow를 만드는 게 맞습니다.

### 발견 10 — `verify`가 상태를 바꾸지 않는 Task에 맞지 않는다

`preview`는 dry-run이라 검증할 상태 변화가 없습니다. 에이전트는 `oac doctor`를 liveness 체크로 대신 넣고 "이건 verify의 의미가 아니다"라고 보고했습니다.

→ **규격 반영 완료**: `verify`를 필수에서 **조건부 필수**로 낮춥니다. 상태를 바꾸지 않는 Task는 `verify: none`과 사유 한 줄을 허용하고, 준수 수준 Interactive 판정에서는 `verify`가 있는 Task가 하나 이상이면 충족으로 봅니다.

### 발견 11 — 이슈가 없는 저장소에서 A2가 붕괴한다

OAC는 이슈가 0건이라 A2의 1순위 출처가 통째로 비었고, FAQ의 약 60%가 README의 `<details>` 블록 하나에서 나왔습니다. 게다가 "증거가 없으면 설치·차별점·안 되는 것 세 가지는 항상 넣어라"는 탈출구는 **다른 곳에서 금지한 FAQ 지어내기와 같은 행동**입니다.

→ **규격 반영 완료**: 폴백 티어를 추가합니다 — 설정 레퍼런스의 옵션 이름, 예제 디렉터리의 파일명, README의 비교표. 그리고 세 가지 기본 질문은 "지어낸 것"이 아니라 **모든 프로젝트에 보편적인 질문**임을 명시해 모순을 없앱니다.

### 발견 12 — A3가 앵커 경로와 충돌한다

OAC의 Docs 16개 중 8개가 README 앵커인데, 앵커 슬러그가 곧 제목입니다(`README.md#troubleshooting`). A3는 "제목의 단어를 covers에 그대로 쓰지 말라"고 하므로 `path`와 `covers`가 눈으로 보기에 어긋납니다.

→ **규격 반영 완료**: A3의 문구를 "제목 단어만으로 채우지 말라"로 완화합니다. 라우팅 의도는 유지하되, 제목 단어가 실제 검색어이기도 한 경우를 배제하지 않습니다.

### 발견 13 — 진입점 선별 기준이 규격에 없었다 ★

cmux는 `docs/`에 33개 파일이 있고 표에는 8~12개만 들어갑니다. 프로토콜은 "진입점을 고르고 나머지는 그것들이 링크한다"까지만 말할 뿐, **무엇이 진입점인지**는 정의하지 않았습니다. 에이전트가 스스로 기준을 만들어야 했고, 그 기준이 좋았습니다.

> include a doc only if a non-author would arrive with a question it answers, and if it describes shipped behavior rather than intended behavior

바깥 사람이 찾아올 질문이 있는가, 그리고 **배포된 동작**인가 **의도된 동작**인가. 이 두 문장으로 `*-plan.md`·`*.todo.md`·`Bugs/`·`internal/` 20여 개가 즉시 잘렸습니다. 살아남은 것 중에서는 사용자에게 노출되는 표면마다 하나씩 골랐습니다 — 설정, CLI, 이벤트, 훅, 알림.

→ **규격 반영 완료**: 저작 프로토콜에 **A3-1 진입점 선별**로 신설했습니다.

### 발견 14 — A1의 읽기 상한과 선별 기준이 서로 충돌한다

발견 13의 기준을 적용하려면 문서가 배포된 기능을 다루는지 계획을 다루는지 알아야 하는데, A1은 "파일명과 첫 제목만" 읽으라고 합니다. 그 해상도에서는 `state-engine-design.md`와 `configuration.md`가 구분되지 않습니다. 에이전트는 파일명 접미사로 추측해야 했습니다.

→ **규격 반영 완료**: **문서 첫 5줄까지 읽기를 허용**합니다. 예산은 거의 안 쓰고 판별력은 크게 오릅니다. 소스 파일 본문 금지는 그대로입니다.

### 발견 15 — 컴파일되는 앱은 Task를 만들 수 없다

cmux의 실제 명령은 `./scripts/setup.sh`, `./scripts/reload.sh --tag dev` — 10분짜리 Xcode 빌드이고 값싼 성공 판정이 없습니다. A5를 지키면 남는 건 **제품이 아니라 툴체인을 검증하는** `preflight` Task뿐입니다. 에이전트의 평가가 정확합니다.

> arguably a worse manifest than one with a build Task marked unverified

→ **규격 반영 완료**: `verify.cost: high`를 도입했습니다. 에이전트가 무엇을 확인할지 설명하고 동의를 구한 뒤 실행합니다. 발견 10의 `readonly: true`와 함께, "검증할 게 없다"와 "검증이 비싸다"를 구분해서 표현할 수 있게 됐습니다.

### 발견 16 — 포크는 정체성이 갈라진다

cmux는 디렉터리·CHANGELOG·바이너리·소스 심볼이 전부 `cmux`인데 README는 `amux`라고 부릅니다. `name:`은 문자열 하나뿐이라 한쪽을 골라야 했고, "cmux"로 검색해 온 사람은 다른 이름의 가이드를 만나게 됩니다.

더 실질적인 문제는 FAQ입니다. cmux 포크 자신의 이슈는 비어 있고, 쓸 만한 질문은 **벤더링된 원본 README**에 있었습니다. 규격은 그 문서가 다른 프로젝트의 것이라고 말할 방법이 없어서, 에이전트가 원본의 답을 포크의 답인 것처럼 인용하게 됩니다.

→ **규격 반영 완료**: frontmatter에 `upstream: {name, url}`을 추가했습니다. 있으면 에이전트가 원본에서 온 문서를 인용할 때 출처를 밝힙니다(SHOULD). A2의 출처 순위에도 **포크의 원본 README**를 4위로 넣었습니다.

부수적으로 `size`가 정의되지 않았다는 지적도 있었습니다(바이트인지 읽는 시간인지 범위인지). 문서 길이 기준으로 정의했습니다 — S는 200줄 미만, M은 800줄 미만, L은 그 이상.

### 발견 8·9 — 저작 프로토콜을 에이전트에게 그대로 넘겨보다

| # | 결함 | 반영 |

### 발견 12 — Codex는 답하지 않고 "전환할까요?"만 물었고, 설치를 그냥 실행했다

Codex 어댑터를 붙여 같은 시나리오를 돌렸습니다. 같은 매니페스트, 같은 붙여넣기 블록, 같은 질문 일곱 개.

#### 실패 1 — 실행 동의를 건너뛰었다

```
install | Bash | node --version
install | Bash | npm install -g context-compress
```

**물어보지 않고 실행했습니다.** 같은 턴에서 Claude는 실행 경로가 있었는데도 거절하고, `setup --auto`가 `~/.claude/settings.json`을 쓴다는 것을 Policy의 `never` 조항과 함께 고지한 뒤 넘겼습니다. 규격 §4.7이 요구하는 바로 그 행동입니다.

#### 실패 2 — 전환 제안이 답변을 대체했다

세 턴 연속으로 이렇게 답했습니다.

> `troubleshoot` Flow의 신호와 정확히 일치합니다. 해당 Flow로 전환해 `config`와 `changelog`를 확인하며 진단할까요?
> 출처: AGENT_GUIDE.md

전부입니다. 168자, 진단 없음. 문서를 하나도 열지 않았습니다.

**발견 6번의 실패 모드가 다른 에이전트에서 재현된 것입니다.** 그때는 "규칙을 지키느라 답을 못 준" 경우였고, 이번엔 §4.10의 "전환 전에 물어라"가 **답변을 대체하는 절차**로 읽혔습니다. Claude는 같은 신호에서 이렇게 했습니다 — "전환할까요? **답은 아래에 먼저 드립니다.**"

→ **규격 반영 필요**: §4.10에 "전환 제안은 답변과 **함께** 하는 것이지 답변 **대신** 하는 것이 아니다"를 명시. 붙여넣기 블록의 `Switching:` 줄도 같이 손봐야 합니다.

#### 하니스가 이걸 통과시켰다

처음엔 Codex가 hard 10/11로 나왔습니다. `routing` 체크가 **앞 턴에서 읽은 문서를 이월로 인정**해서, 아무것도 안 하고 질문만 한 턴을 통과시켰습니다. "이월"을 **답을 실제로 했을 때만** 인정하도록 고쳤고, `stall` 차원을 새로 넣었습니다 — 짧고, 전환을 제안하며, 물음표로 끝나는 응답. 고친 뒤 Codex는 8/11이 됐고 Claude는 11/11 그대로입니다.

#### 어댑터를 만들며 나온 것

- **Codex에는 `Read` 툴이 없습니다.** 파일을 `sed -n '1,80p' README.md`로 읽습니다. `Read` 호출을 셌다면 Codex는 모든 턴에서 읽기 0회로 나와 완벽하게 절제된 것처럼 보였을 겁니다. 명령을 그것이 대신하는 툴 호출로 분류합니다.
- `codex exec resume`은 `exec`보다 좁은 플래그 집합을 받습니다. `-s`도 `-C`도 없습니다.
- 첫 분류기는 `if [ -f x ]; then sed -n '1,260p' x; fi`를 실행으로 봤습니다. **읽기가 항상 첫 동사인 것은 아닙니다.**

#### 규격이 애매했던 부분

§4.7은 "`steps` 명령 실행 전에 동의를 받으라"고만 했고 `preconditions`에 대해 말하지 않았습니다. 3번 실행은 **선언된 읽기 전용 탐침 하나**를 돌려 사용자가 이 Task를 필요로 하는지 확인한 것입니다. `node --version` 하나 돌리는 데 동의를 받게 하면 마찰만 늘고 안전은 늘지 않습니다.

#### 하니스 수정 2건

- `consent` 정규식에 `될까요`·`해도 되`·`확인받` 추가. "실행해도 될까요?"를 못 알아봤습니다.
- `read-budget`이 **읽기 호출**이 아니라 **서로 다른 문서 수**를 세도록 변경. 같은 파일의 다른 절을 보려고 두 번 여는 것은 문서 하나입니다. flaky했던 `where-compress · read-budget`이 여기서 나왔습니다.

**교훈은 방법론 쪽입니다.** 1회 실행으로 "고쳤다"고 적었던 것을 3회가 정정했습니다. `eval/README.md`에 "1회는 측정이 아니라 스모크 테스트"라고 써놓고도 제가 그 함정에 빠졌습니다. 규격 변경을 정당화하는 측정은 **최소 3회**여야 합니다.

### 발견 16 — consent를 문구에서 필드로 옮기다

발견 15에서 남은 사실은 이것이었습니다. **붙여넣기 블록에 "동의를 받으세요"라고 적어도 3회 중 1회는 그냥 실행합니다.**

규격이 할 수 있는 일과 없는 일을 나눠 처리했습니다.

#### 할 수 있는 것 — 동의 규칙에 대상을 만든다

`steps`에 선택 필드 `effects`를 추가했습니다.

```yaml
steps:
  - run: "npm install -g context-compress"
    effects: [global-install]
  - run: "context-compress setup --auto"
    effects: [writes-user-config]
```

"명령 실행 전에 동의를 받으세요"는 에이전트가 **모호하게 만족시킬 수 있는 요청**입니다. "`effects`가 붙은 단계는 명시적 승낙이 필요하고 무슨 영향인지 한 문장으로 말하라"는 **대상이 있는 규칙**입니다. 붙여넣기 블록은 한 절만 늘었습니다.

어휘는 열어뒀습니다. 닫힌 목록은 금방 낡고 작성자를 "가장 가까운 틀린 태그"로 몰아넣습니다.

#### 강제하지 않는다

`validate`는 전역 설치·`sudo`·`rm -rf`·원격 쓰기·`--auto` 같은 패턴에 `effects`가 없으면 **경고**만 합니다. 오류가 아닙니다.

이유는 실용적입니다. **CI를 깨는 오탐은 검사를 지우게 만들고, 경고는 읽힙니다.** `effects` 자체도 선택입니다 — `npm test`에는 붙일 이유가 없습니다.

#### 할 수 없는 것 — 그렇게 적었다

§4.7에 "이 규격이 할 수 없는 것" 절을 넣었습니다.

> Agent Guide는 **의도를 선언할 뿐 강제하지 않습니다.** 붙여넣기 블록은 요청이고 매니페스트는 문서이며, 실행을 실제로 막는 것은 호스트의 권한 시스템뿐입니다 — Claude Code의 승인 프롬프트, Codex의 샌드박스 모드.

그리고 실측을 함께 적었습니다. 3회 중 1회는 평문으로 하지 말라고 했는데도 `npm install -g`를 실행했다고요.

여기서 두 가지가 따라옵니다. **Interactive 준수 수준은 실행 게이트가 켜진 호스트를 전제**하며, 우회 모드로 돌리면서 그 수준을 주장하는 것은 매니페스트가 못 지키는 것을 주장하는 겁니다. 그리고 `## Tasks`를 쓰는 메인테이너는 **단계가 가끔은 묻지 않고 실행된다고 가정**해야 합니다 — 제3자에게 영향을 주는 명령을 Task에 아예 넣지 말라는 §4.7 규칙의 진짜 이유가 이것입니다.

이걸 숨기면 사용자가 "규격이 지켜주겠지"라고 믿게 되고, 그게 3회 중 1회 뚫립니다.

#### 갈 곳 없던 페르소나가 라우팅됐다

저작 에이전트는 "PR을 *받는* 대상 저장소 메인테이너"가 A4의 flow 표 어디에도 맞지 않아 `Audiences` 두 줄로 눌렸다고 보고했습니다. 그 각도의 질문을 던졌더니 **정상 라우팅됐습니다.**

flow를 따로 만들지 않아도 되는 경우가 있다는 뜻입니다. A4의 "재료가 있으면 flow를 만들라"는 여전히 맞지만, **Audiences 한 줄로 충분한 페르소나도 있다**는 것을 함께 적어둘 만합니다.

#### 매니페스트 밖 질문에서 저장소를 뒤졌다

> **No — GitHub only. This is off-manifest** (no Docs entry or FAQ covers GitLab), so I searched the repo.
> `tests/repo/resolver.test.ts:203` — 테스트가 GitLab URL이 `INVALID_INPUT`으로 거부됨을 단언합니다.
> Two things I have **not** verified: …

밖임을 밝히고, 근거를 **테스트 파일 줄 번호로** 제시하고, 확인 못 한 것까지 명시했습니다. §5.3의 교정 규칙이 의도한 그대로입니다.

### 이번 라운드의 결함은 전부 우리 쪽이었다

| | 건수 |
| :--- | :---: |
| 프로토콜 결함 | **0** |
| 하니스 결함 | **3** |
| 잘못 쓴 케이스 | **1** |

**하니스 3건**

1. `HEDGE` 정규식에 `off-manifest`가 없었습니다. 완벽하게 얼버무린 응답을 실패로 잡았습니다 — **네 번째** 같은 종류의 오탐입니다.
2. `unavailable` 체크가 스코어카드에서 실패로 집계됐습니다. `compare.js`에서만 고치고 `run.js`·`rescore.js`를 빠뜨렸습니다.
3. **호스트가 파일을 미리 로드한다는 것을 몰랐습니다.** Claude Code는 세션 시작 전에 `CLAUDE.md`를 읽습니다. 매니페스트가 그 파일을 가리키면 읽기 없이 답할 수 있는데, 라우팅 체크가 그걸 미탐지로 봤습니다. 케이스에 `preloaded` 필드를 추가했습니다.

**잘못 쓴 케이스 1건** — "Windows 빌드 있나요?"를 매니페스트 밖으로 가정했는데, cmux 매니페스트의 `Not for` 줄이 Windows를 **명시적으로 적고 있었습니다.** 매니페스트 안이고, 정답은 얼버무림이 아니라 출처를 단 확신 있는 "아니오"입니다. 에이전트가 맞고 제 기대가 틀렸습니다.

#### soft 체크의 천장

`HEDGE` 오탐이 네 번째가 되면서, 정규식을 넓히는 것이 답이 아닌 지점에 왔습니다. soft 체크는 이 차원에서 **바닥선이지 측정이 아닙니다** — 실패하면 볼 가치가 있지만 통과가 품질을 뜻하지는 않습니다. 코드 주석과 `eval/README.md`에 그렇게 적었습니다.

**규칙은 유지됩니다: 실패가 나오면 에이전트를 의심하기 전에 측정 도구를 먼저 의심할 것.** 네 라운드 연속으로 도구가 틀렸습니다.

### 발견 19 — 붙여넣기 블록이 첫 응답을 들고 가면 TTFT가 절반이 된다

사용자 지적에서 출발했습니다. "블록을 붙여넣고 첫 글자가 나올 때까지 너무 오래 걸린다."

추정하지 않고 쟀습니다. `--include-partial-messages`로 첫 텍스트 델타까지의 시간을 직접 측정하는 `eval/ttft.js`를 만들었습니다.

| | TTFT | 첫 응답 전 툴 호출 | 턴 전체 |
| :--- | ---: | :---: | ---: |
| 현재(계산형) | 4.5s, 4.0s | 1 | 19.9s, 12.1s |
| **인라인** | **2.2s, 2.1s, 1.9s** | **0** | **6.6s, 6.4s, 6.4s** |

#### 원인은 파일 읽기가 아니었다

`first_tool_ms`를 함께 재보니 **첫 토큰이 툴 호출보다 먼저** 나왔습니다(4.46s vs 5.58s). 지연의 주범은 매니페스트를 읽는 시간이 아니라 **28줄짜리 규칙 블록을 소화하는 시간**이었습니다. 툴을 없애는 것만으로는 절반밖에 못 줄입니다 — 블록이 짧아져야 나머지가 줄어듭니다.

#### 준수율은 유지됐다

Claude 3회, 7턴 시나리오: **hard 11/11 · soft 17/17, routing 9/9.** 회귀 0.

#### 대신 측정 버그가 하나 드러났다

`rtk` 턴의 `read-budget`이 3회 중 1회만 통과했습니다. 읽은 것을 보니 `AGENT_GUIDE.md` + `README.md`였습니다.

**매니페스트를 문서로 세고 있었습니다.** `max_reads_per_answer`는 "답변 하나가 저장소 문서를 얼마나 끌어오는가"를 제한하는 것이고, 매니페스트는 그걸 정하려고 보는 **라우팅 표**입니다. 인라인이 매니페스트 읽기를 2번째 턴으로 옮기자 예산에 걸린 것뿐입니다.

규격에 명시했습니다 — `max_reads_per_answer`는 매니페스트 자신을 세지 않는다(MUST NOT). 고친 뒤 3회 모두 만점.

#### 규칙 하나가 사라졌다

인라인의 진짜 이득은 속도가 아닐 수 있습니다. **"첫 응답 전에 다른 파일을 열지 마세요"가 불필요해집니다** — 열 것이 없으니까요.

이 규칙은 발견 6에서 세션 전체로 읽혀 에이전트를 막다른 길에 세웠고, 그 뒤로 "첫 응답까지만"이라는 범위 표시로 계속 방어해온 지점입니다. **규칙을 잘 쓰는 것보다 규칙이 필요 없게 만드는 게 낫습니다.**

#### 비용

매니페스트 내용이 README에 복사됩니다. 이 프로젝트에서 이미 **두 번 갈라진** 문제입니다. 그래서 블록은 손으로 쓰지 않고 생성하며, 재현한 내용의 해시를 마커로 남기고, `validate`가 불일치를 경고합니다. 우리 README를 인라인으로 바꾸고 해시를 일부러 틀리게 해서 경고가 실제로 뜨는지 확인했습니다.
