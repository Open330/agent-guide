## 1. 문제

오픈소스 프로젝트의 온보딩은 여전히 "README를 읽는다"를 전제로 설계되어 있다. 그런데 지금 코드를 만지는 주체는 상당 부분 에이전트로 옮겨갔고, 사람은 README를 끝까지 읽지 않는다.

현재 벌어지는 일:

- **사람**: README 상단 3줄과 설치 커맨드만 복사하고 나머지는 건너뛴다. 설계 의도, 제약, 안 되는 것은 전달되지 않는다.
- **에이전트**: 저장소를 통째로 grep 하거나 컨텍스트에 우겨넣고 요약한다. 토큰은 많이 쓰는데 정확도는 낮고, 문서에 없는 API를 자신 있게 지어낸다.
- **메인테이너**: 같은 질문이 이슈로 반복 유입된다. FAQ를 문서에 추가해도 아무도 그 문서까지 도달하지 못한다.

핵심은 문서가 부족한 게 아니라 **문서로 가는 진입점과 탐색 경로가 기계가 읽을 수 있는 형태로 존재하지 않는다**는 점이다.

## 2. 해결 가설

README에는 문서 대신 **초기 프롬프트 한 덩어리**를 둔다. 사용자는 그것을 자기 에이전트에 붙여넣는다. 에이전트는 프로젝트가 제공한 매니페스트 `AGENT_GUIDE.md`를 읽고 **대화형 세션**을 진행한다.

읽는 문서를 **진행하는 세션**으로 바꾼다.

```
README의 프롬프트 복사
      ↓ 붙여넣기
에이전트가 AGENT_GUIDE.md 로드 (1회 fetch)
      ↓
개요 3문장 + 안 맞는 사례 + "무엇을 하려 하는가"(flow 선택) + FAQ
      ↓
질문 → 매니페스트가 지정한 문서만 선택적으로 열람 → 출처 붙여 답변
      ↓
설치·마이그레이션 같은 실행 과제는 동의를 받고 수행·검증
      ↓
막히면 다른 flow로 전환했다가 돌아옴
```

## 3. flow — 온보딩은 시작점일 뿐

초기 구상은 온보딩에 한정되어 있었으나, 같은 뼈대가 훨씬 넓게 쓰인다는 점이 분명해졌다. **flow**는 하나의 대화 세션 유형이고, 온보딩은 그중 하나다.

| flow | 언제 |
| :--- | :--- |
| `onboard` | 처음 왔다. 나에게 맞는 도구인지 판단하고 첫 성공까지 |
| `integrate` | 우리 서비스·CI에 붙인다 |
| `upgrade` | 버전을 올린다. 깨지는 변경 파악부터 변환까지 |
| `troubleshoot` | 안 된다. 증상에서 원인 문서까지 최단 경로로 |
| `contribute` | 구조를 이해하고 첫 PR까지 |

`## Docs`·`## Code map`·`## Tasks`는 공유 자산이고 flow가 그것을 id로 조합한다. 새 flow를 추가하는 비용이 FAQ 몇 줄로 떨어지므로, **메인테이너가 릴리스마다 마이그레이션 flow를 하나씩 얹는** 그림이 자연스럽게 성립한다. 매니페스트가 낡는 문제도 여기서 같이 풀린다.

flow **전환**이 이 프로토콜의 요지다. 설치 중 에러가 나면 `troubleshoot`으로 넘어갔다가 돌아온다. 정해진 순서를 따라가는 게 아니라 대화가 경로를 정한다.

## 4. 목표와 비목표

### 목표
1. 메인테이너가 **파일 하나(`AGENT_GUIDE.md`) + README 블록**만 추가하면 세션이 성립한다.
2. 특정 에이전트에 종속되지 않는다. Claude Code, Cursor, Codex, ChatGPT 웹, Copilot 어디에 붙여넣어도 동작한다.
3. 에이전트가 **저장소 전체를 읽지 않고도** 정확히 답한다. 첫 응답까지의 읽기 횟수를 규격으로 제한한다.
4. 모르는 것은 지어내지 않고 "매니페스트에 없다"고 말한 뒤 이슈 링크로 넘긴다.

### 비목표
- 코드 기여 규약을 정의하는 것. 그건 `AGENTS.md`의 영역이고, 우리는 참조하고 넘겨준다.
- 문서 자체를 생성하거나 대체하는 것. 우리는 **경로와 진행 절차**를 정의한다.
- 별도 호스팅 서비스나 런타임 데몬. v0.1은 정적 파일과 프롬프트만으로 완결된다.

## 5. 기존 표준과의 관계

| | 대상 | 형태 | 성격 |
| :--- | :--- | :--- | :--- |
| `llms.txt` | LLM 일반 | 링크 목록 | 정적 색인, 단발 조회 |
| `AGENTS.md` | 코딩 에이전트 | 자연어 규약 | 기여자 규칙 |
| `apm.yml` | 에이전트 배포 | 매니페스트+락파일 | 에이전트 구성의 재현 가능한 설치 |
| **`AGENT_GUIDE.md`** | **사람 ↔ 에이전트 대화** | **매니페스트 + 세션 프로토콜** | **상태를 가진 세션, 의도 라우팅, 실행·검증** |

경쟁이 아니라 계층이 다르다. 이 표를 README 상단에 그대로 실어서 "표준이 또 하나 늘었다"는 반발을 미리 차단한다.

AGENTS.md는 이미 6만 개 이상의 저장소가 채택했고 Linux Foundation 산하 AAIF로 거버넌스가 넘어갔다. 그 옆자리를 노리되 **부록으로 보이지 않는 것**이 중요하다. 파일명을 복수형 `AGENTS_GUIDE.md`가 아니라 단수 `AGENT_GUIDE.md`로 정한 이유도 그것이다.

## 6. 사용자와 시나리오

### 6.1 평가자 — "이거 나한테 필요한 건가"

> 사용자: (프롬프트 붙여넣기)
>
> 에이전트: **foo**는 팀 단위 프롬프트 버전 관리 도구입니다. 프롬프트를 코드처럼 Git으로 관리하고, 배포 전 회귀 평가를 자동으로 돌립니다. 현재 beta이고, 프로덕션 트래픽 라우팅과 파인튜닝은 다루지 않습니다.
>
> 무엇을 하려고 오셨나요?
> 1. 처음 왔어요 (기본)  2. 우리 CI에 붙이기  3. v1 → v2 마이그레이션  4. 안 될 때  5. 기여하기
>
> 자주 나오는 질문:
> - 설치는 어떻게 하나요?
> - LangSmith나 Braintrust와 뭐가 다른가요?
> - 셀프호스팅이 되나요?

여기서 끝나는 게 절반이다. 그리고 그 절반은 **정확한 이유로** 끝나야 한다. 그래서 `Not for`를 필수 필드로 넣었다. 맞지 않는 사용자를 빨리 돌려보내는 것도 성공이다.

### 6.2 도입자 — "설치하고 첫 성공까지"

> 사용자: 설치 방법 알려줘
>
> 에이전트: (Task `install`을 읽음) Node 20 이상이 필요합니다. 지금 환경은 22.3이라 조건은 맞습니다. 두 단계를 실행할까요?
> 1. `npm i -g foo`  2. `foo doctor` — 설치 검증
>
> 사용자: 응
>
> 에이전트: (실행) 설치됐습니다. `foo doctor`가 API 키 없음을 보고합니다. `on_fail`이 가리키는 문서에 따르면 `FOO_API_KEY`가 필요하고 발급 경로는 여기입니다. [출처: docs/quickstart.md#api-key]

읽기만 하는 온보딩과 결정적으로 갈리는 지점이다. 명령을 **실행하고, 규격에 정의된 방법으로 성공을 검증하고, 실패하면 지정된 문서로 분기**한다.

### 6.3 기여자 — "구조를 이해하고 첫 PR까지"

> 사용자: 인증 부분 고치려면 어디를 봐야 해?
>
> 에이전트: (Code map 조회) `src/auth/` 아래 세션 발급과 토큰 검증이 나뉘어 있습니다. 설계 배경은 ADR-004에 있고, 세션 저장소를 Redis로 고정한 이유가 거기 설명됩니다. 관련 테스트는 `tests/auth/`입니다. 열어서 요약할까요? [출처: AGENT_GUIDE.md#code-map, docs/adr-004.md]

Code map은 "어느 디렉터리가 무엇을 담당하는지"의 거친 지도다. 이게 있으면 에이전트가 저장소를 훑는 대신 곧장 목적지로 간다.

### 6.4 flow 전환 — 프로토콜의 요지

> 사용자: 설치는 됐는데 `foo eval`이 계속 실패해요
>
> 에이전트: 문제 해결 flow로 잠깐 넘어갈까요? 진단 정보부터 모으겠습니다. 끝나면 원래 하시던 첫 평가 실행으로 돌아옵니다.

| **예제** | 최소 예제, 실전 예제, 본 저장소 자체의 매니페스트 | `examples/` |

### 왜 Markdown인가

**1차 소비자가 파서가 아니라 LLM이다.** 보통 데이터 포맷이 이기는 건 프로그램이 읽기 때문인데, 여기서는 에이전트가 읽는다. 에이전트는 잘 구조화된 Markdown을 중첩 YAML만큼 안정적으로 읽는다. 그럼 YAML이 남기는 이점은 엄격한 검증과 툴링뿐이고, 그건 M2의 부차적 관심사다.

실질적 이유는 세 가지다. 작성 장벽이 낮고(도입의 유일한 병목이 매니페스트 작성이다), GitHub 저장소 화면에서 렌더링되어 사람도 읽으며(그래야 메인테이너가 최신으로 유지한다), 선례가 이쪽이다(README·AGENTS.md·SKILL.md·CLAUDE.md).

정밀함이 필요한 곳 — frontmatter와 Tasks·Policy — 만 YAML 블록으로 남긴다. 실행 명령과 검증 정규식이 애매하면 위험하기 때문이다.

### 초기 프롬프트의 설계 제약

이 블록이 사실상 제품의 전부다.

- **자기완결**: 규격 문서를 추가로 받아오지 않아도 첫 턴이 성립해야 한다. 세션 규칙을 프롬프트 안에 인라인으로 넣는다. 외부 fetch는 매니페스트 한 번뿐이다.
- **짧음**: 20줄 이내. 길면 아무도 복사하지 않는다.
- **원격/로컬 이중 경로**: 클론하지 않은 사용자는 raw URL로, 클론한 사용자는 로컬 경로로 읽는다.
- **네트워크 없는 에이전트 대비**: fetch가 막히면 사용자에게 파일 내용을 붙여넣어 달라고 요청하도록 지시한다.

### CLI가 하는 일

`npx agent-guide init`은 빈 템플릿을 만들어 주는 게 아니라 **저장소를 훑어 초안을 채운다**. `docs/` 트리, `package.json`, 기존 `README.md`·`AGENTS.md`·`llms.txt`를 읽고 매니페스트 초안과 README 블록을 함께 생성한다. 작성 부담이 도입의 유일한 병목이므로 여기에 힘을 준다.

## 8. 성공 지표

| 구분 | 지표 | 목표 |
| :--- | :--- | :--- |
| 도입 | `AGENT_GUIDE.md`를 둔 공개 저장소 수 | 3개월 40개 |
| 마찰 | `init` 실행부터 커밋까지 걸린 시간 | 중앙값 10분 이하 |
| 품질 | 첫 응답까지 에이전트가 연 파일 수 | 2개 이하 (규격상 상한) |
| 품질 | 평가 시나리오 정답률(출처 인용 포함) | 90% 이상 |
| 확장 | 도입 저장소당 평균 flow 수 | 2개 이상 (온보딩 전용에 머물지 않았다는 신호) |
| 효과 | 도입 저장소의 "설치/사용법" 유형 이슈 비중 | 도입 전 대비 감소 |

품질 지표는 주장이 아니라 측정 대상이다. 예제 저장소 3개에 대해 질문 20개 규모의 평가셋을 만들고, 여러 에이전트에서 정답률·읽은 파일 수·환각 여부를 재는 하니스를 M3에 포함한다.

## 9. 리스크

| 리스크 | 대응 |
| :--- | :--- |
| "표준이 또 하나 늘었다"는 반발 | 경쟁이 아닌 계층으로 포지셔닝. 기존 `llms.txt`/`AGENTS.md`를 Docs 표로 흡수 |
| AGENTS.md의 부록으로 오해 | 단수 파일명, README 첫 화면에 계층 비교표 |
| Markdown이라 검증이 느슨함 | 열 순서·영문 섹션 키를 규범으로 고정. `validate`는 경로 존재와 id 해석까지 검사 |
| 매니페스트가 코드와 함께 낡음 | `validate`를 CI 액션으로 제공. 사람이 읽는 문서라 갱신 동기가 생기는 것도 이 포맷의 이점 |
| 에이전트가 프로토콜을 안 지킴 | 규칙을 짧고 명령형으로. 준수 여부를 평가 하니스로 측정하고 모델별 결과를 공개 |
| 제어를 벗어난 명령 실행 | 실행 전 동의 필수, `## Tasks`에 선언된 명령만 실행하도록 규격에 명시 |
