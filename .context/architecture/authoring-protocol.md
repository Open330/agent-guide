# 저작 프로토콜 — 에이전트가 `AGENT_GUIDE.md`를 쓰는 방법

Last Updated: 2026-08-27
Status: Draft

규격의 나머지 절반. [guide-spec-draft.md](guide-spec-draft.md)가 **읽는 쪽**을 정의한다면, 이 문서는 **쓰는 쪽**을 정의한다.

---

## 1. 왜 별도 프로토콜이 필요한가

에이전트에게 "AGENT_GUIDE.md를 써줘"라고만 하면 거의 예외 없이 **README 요약본**이 나온다. 그건 실패다. 매니페스트의 가치는 문서를 요약하는 데 있지 않고, **사용자가 실제로 던지는 질문과 그 답이 있는 위치를 잇는 데** 있다.

즉 저작은 요약 작업이 아니라 **증거 수집 작업**이다. 이 프로토콜은 그 차이를 절차로 강제한다.

| 잘못된 저작 | 올바른 저작 |
| :--- | :--- |
| README를 읽고 요약한다 | 사용자가 무엇을 묻는지 증거를 모은다 |
| 문서 제목을 질문형으로 바꿔 FAQ를 만든다 | 이슈·트러블슈팅에 실제로 나온 문장을 가져온다 |
| covers에 문서 제목의 단어를 넣는다 | 질문자가 쓸 단어를 넣는다. 에러 메시지 원문도 좋다 |
| flow 다섯 개를 골고루 채운다 | 증거가 있는 flow만 만든다 |
| 그럴듯한 `verify` 명령을 지어낸다 | 실제로 실행해보고 확인한 명령만 쓴다 |

## 2. 절차

### A1. 수집 — 예산을 정해놓고 읽는다

다음 순서로 읽고, **파일 열람 15회를 넘기지 않는다**(SHOULD).

1. `README.md` — 제목 목록 전체 + 앞 200줄
2. 패키지 매니페스트 — `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod`
   → 이름, 실행 파일명, 런타임 요구사항, 스크립트
3. `docs/` 트리 — 파일명과 각 파일의 첫 제목만
4. `AGENTS.md` · `CONTRIBUTING.md` · `CLAUDE.md` · `SECURITY.md` — 있으면 존재만 확인
5. `CHANGELOG.md` — 최신 릴리스의 breaking change 절
6. 최상위 소스 디렉터리 이름 (1단계 깊이까지, 내용은 읽지 않음)

**소스 파일 본문을 읽지 않는다**(MUST NOT). Code map은 디렉터리 이름과 그 안의 파일 이름만으로 쓴다. 거친 지도가 목적이고, 정확한 지도를 만들려다 예산을 태우는 것이 이 단계의 가장 흔한 실패다.

**문서는 첫 5줄까지 읽어도 된다.** 파일명과 첫 제목만으로는 *배포된 기능을 설명하는 문서*와 *설계 계획 문서*를 구분할 수 없다. `state-engine-design.md`와 `configuration.md`는 그 해상도에서 똑같아 보인다. 5줄이면 대개 판별되고, 예산도 거의 쓰지 않는다.

### A2. FAQ 도출 — 지어내지 말고 캐낸다

질문의 출처를 **우선순위 순으로** 뒤진다.

| 순위 | 출처 | 왜 |
| :-: | :--- | :--- |
| 1 | GitHub Issues의 `question`·`help wanted` 라벨 | 실제로 나온 질문. 최고 품질이지만 **비어 있는 경우가 많다** |
| 2 | CHANGELOG의 버그 설명과 breaking change | "왜 안 되지"의 원문. 실측상 가장 안정적인 광맥 |
| 3 | README의 FAQ·Troubleshooting·`<details>` 접힌 절 | 접어둔 건 자주 막히는 지점이라는 뜻 |
| 4 | 포크라면 **원본의 README·FAQ** | 포크 자신의 이슈는 비어도 원본에는 쌓여 있다 |
| 5 | README의 비교표·"vs" 절 | 도입 검토자의 첫 질문 |

1위가 비는 일이 흔하다. 실험한 저장소 세 곳 중 두 곳에서 `question` 라벨 이슈가 0건이었다. **1위가 비었다고 멈추지 말고 2위로 내려간다.**

다만 **정말 빈 것과 조회가 실패한 것을 구분한다**(MUST). 라벨 없이 한 번 더 조회해보고, 그래도 0건이면 원격과 인증이 살아 있는지 확인한다. 확인이 안 되면 A7의 확인 요청에 **"이슈 증거 없이 FAQ를 작성했다"**고 적는다. 이슈가 정말 없는 프로젝트인지 조회가 막힌 것인지는 메인테이너만 안다. 잘 쓴 CHANGELOG는 "사람들이 여기서 막혔다"를 이미 문장으로 적어놓은 문서다.

증거가 전혀 없으면 **FAQ를 지어내지 않는다.** 증거가 없다는 사실 자체가 메인테이너에게 보고할 발견이다.

다만 **설치·다른 것과의 차이·안 되는 것** 세 가지는 예외로 허용한다. 거의 모든 프로젝트에서 답이 문서에 이미 존재하기 때문이다. 단 조건이 있다 — `answer_from`이 **실제로 존재하는 문서**를 가리켜야 한다(MUST). 답할 문서가 없는 질문은 FAQ가 아니라 문서 개선 요청이다.

FAQ 질문은 **사용자의 말**로 적는다(MUST). 문서 제목을 물음표로 바꾼 것은 금지한다.

- ○ `설치는 됐는데 아무 일도 안 일어납니다`
- ✗ `설치 방법은 무엇인가요?` (제목 `## Install`을 뒤집은 것)

### A3. covers — 검색어로 쓴다

문서마다 "이 문서가 필요한 사람이 뭐라고 칠까"를 3~7개 적는다. 규칙:

- 문서 제목의 단어를 그대로 쓰지 않는다. **예외**: 경로가 README 앵커(`README.md#troubleshooting`)면 슬러그가 곧 제목이라 겹칠 수밖에 없다. 이 규칙은 라우팅 품질을 위한 것이지 글자 회피가 목적이 아니므로, 앵커와의 겹침은 허용한다.
- **에러 메시지 원문**은 최상급 covers다. `HTTP 403`, `command not found` 같은 것.
- 같은 뜻의 영어·한국어를 함께 넣는다. `설치, install`
- 두 문서의 covers가 겹치면 둘 다 후보로 열리므로 낭비다. 겹치는 부분을 지운다.

### A3-1. 진입점 선별 — 문서가 슬롯보다 많을 때

Docs 표는 **진입점 8~12개**다. 문서가 30개, 40개인 저장소에서는 무엇을 넣을지가 저작의 핵심 판단이 된다. 기준은 두 가지다.

1. **바깥 사람이 이 문서를 찾아올 질문이 있는가.** 저자를 위해 쓴 문서 — 설계 계획, TODO 로그, 버그 노트 — 는 질문의 도착지가 아니다.
2. **배포된 동작을 설명하는가, 의도된 동작을 설명하는가.** `*-plan.md`, `*-spec.md`, `*.todo.md`는 대개 후자다.

살아남은 문서 중에서는 **사용자에게 노출되는 표면마다 하나씩** 고른다. 설정, CLI, 이벤트, 훅, 알림처럼.

**"나머지는 그 문서들이 링크한다"를 그냥 믿지 않는다.** 실측에서 이 전제는 거짓이었다 — 잘라낸 문서 중 여섯 개는 사용자·기여자용인데 남긴 12개 어디에서도 링크되지 않았다. 잘라낸 것 중 하나라도 진입점에서 도달할 수 없으면 Docs 표 마지막에 디렉터리 자체를 한 줄로 넣는다.

```
| more | docs/ | 위에 없는 주제 — 여기부터 찾는다 |
```

한 줄로 "여기 더 있다"를 말할 수 있으면, 슬롯이 모자란다는 이유로 문서를 지도에서 지워버리는 일이 없다.

실측 사례: 문서 33개 중 6개 + README + 원본 README + AGENTS.md + CONTRIBUTING.md + CHANGELOG로 12개를 채웠다. 잘라낸 20여 개는 전부 계획·TODO·내부 문서였다.

### A4. flow — 증거가 있는 것만 만든다

`onboard`는 항상 만들고 `(default)`를 붙인다. 나머지는 조건이 맞을 때만 만든다.

**아래 표는 열거형이 아니라 흔한 사례다.** flow id는 자유이며, 프로젝트에 진짜로 구분되는 두 번째 사용자층이 있으면 그 층을 위한 flow를 만드는 것이 옳다. 예를 들어 에이전트가 만든 PR을 *받는* 대상 저장소의 메인테이너는 onboard·integrate·contribute 어디에도 맞지 않는다. 억지로 `Audiences` 한 줄에 밀어넣지 말고 flow로 분리한다.

| flow | 만드는 조건 |
| :--- | :--- |
| `upgrade` | **버전 사이에 사용자가 체감하는 동작 변화가 있다** (아래 참고) |
| `troubleshoot` | 트러블슈팅 문서가 있거나, 이슈에 오류 문의가 반복된다 |
| `integrate` | CI·SDK·Action·플러그인처럼 남의 시스템에 붙는 성격이다 |
| `contribute` | `CONTRIBUTING.md`나 `AGENTS.md`가 있다 |

`upgrade`의 조건은 **CHANGELOG에 "Breaking"이라고 적혀 있는지가 아니다.** 패키지 이름이 바뀐 일, `engines` 하한이 내려간 일, 버전 번호를 잘못 찍어 패키지 매니저의 정렬이 어긋난 일 — 라벨은 없지만 업그레이드하는 사람이 정확히 여기서 데인다. 라벨이 아니라 **동작 변화**를 본다.

**빈 껍데기 flow를 만들지 않는다**(MUST NOT). FAQ가 한 줄뿐인 flow는 선택지만 늘리고 답은 못 준다. 없는 편이 낫다.

### A5. Tasks — 실행해보고 쓴다

- 명령은 **README의 코드 블록에서 그대로** 가져온다. 손대지 않는다.
- **예외 — 사용자 기계 밖에 영향을 주는 명령**(PR 생성, 배포, 외부 저장소 쓰기, 과금)은 그대로 가져오지 않는다(MUST NOT). `--dry-run` 같은 안전한 변형을 쓰고, 왜 바꿨는지 `explain`에 적는다. 안전한 변형이 없으면 그 Task를 만들지 않고 `Policy.never`에 금지 항목으로 넣는다.
- `verify`는 **실제로 존재하는 명령**이어야 한다. 명령 대신 쓸 수 있는 값이 둘 있고, 각각 `why:` 한 줄이 필요하다.
  - `verify: none` — 바뀌는 게 없는 Task(미리보기, 리포트, 진단). 검증할 사후 상태가 없다.
  - `verify: unverified` — 작성 환경에서 성공을 확인하지 못했다. 빌드가 비싼 프로젝트에서 쓴다.
- 환경 점검 명령을 verify인 척 끼워넣지 않는다 — 그건 Task의 성공이 아니라 전제 조건을 검증하는 것이다.
- **"확인 못 하면 Task를 만들지 마라"는 규칙은 쓰지 않는다.** 그 규칙은 빌드가 비싼 프로젝트에서 가장 중요한 Task를 삭제시킨다. 정직한 `unverified`가 지어낸 `expect`보다 낫고, 둘 다 침묵보다 낫다.
- `expect` 정규식은 실행 결과를 보고 맞춘다. 사용자 동의를 받고 한 번 돌려보는 것이 가장 확실하다.
- `preconditions`는 패키지 매니페스트의 `engines`·`requires-python`에서 가져온다. 매니페스트에 없지만 문서 산문이 요구하는 것(예: `git` 설치)은 넣어도 되며, `hint`에 근거를 적는다. 아무 근거 없는 전제 조건만 금지한다.

### A6. 자가 검증 — 쓴 다음 반드시

1. `Docs`·`Code map`의 **모든 경로가 실제로 존재하는가**. 하나씩 확인한다(MUST).
2. FAQ와 Task의 **모든 id 참조가 해석되는가**.
3. `(default)` flow가 **정확히 하나**인가.
4. 개요가 3문장 이내인가.
5. 각 flow의 FAQ가 **2줄 이상**인가.

### A7. 사람에게 확인받는다 — 생략 불가

다음 세 가지는 저장소를 아무리 읽어도 신뢰할 수 있게 도출되지 않는다. 반드시 메인테이너에게 확인한다(MUST).

| 항목 | 왜 도출이 안 되는가 |
| :--- | :--- |
| **`Not for`** | README는 자기가 못 하는 일을 절대 쓰지 않는다. 그런데 이 줄이 매니페스트에서 가장 값지다 |
| **개요 3문장** | 첫인상은 메인테이너가 직접 통제해야 한다. 에이전트의 요약은 강조점을 자주 틀린다 |
| **`status`** | 저장소에 `alpha`인지 `stable`인지 적혀 있는 경우는 드물다 |

초안에는 채워 넣되 **확인이 필요한 부분을 명시적으로 표시해서 제시한다**(MUST). 조용히 추측해서 넘기지 않는다.

## 3. 흔한 함정

| 함정 | 증상 | 교정 |
| :--- | :--- | :--- |
| README가 곧 문서 전부인 저장소 | `docs/`가 비었다고 Docs 표를 못 씀 | 앵커를 쓴다. `README.md#quickstart` — 경로에 프래그먼트를 붙이면 된다 |
| 문서가 너무 많은 저장소 | 60개 파일을 전부 표에 넣음 | [A3-1](#a3-1-진입점-선별--문서가-슬롯보다-많을-때)의 기준으로 자르고, 도달 못 하는 문서가 남으면 `more` 행을 넣는다 |
| 모노레포 | 어느 패키지 얘기인지 섞임 | 패키지별로 매니페스트를 두거나, flow를 패키지 단위로 나눈다 |
| 이미 `AGENTS.md`가 있음 | 내용이 중복됨 | 중복해서 쓰지 않는다. Docs 표에 넣고 `contribute` flow의 `Next:`로 넘긴다 |
| 문서가 영어, 사용자가 한국어 | 언어가 섞임 | frontmatter `language`로 응답 언어를 정하고, 표의 covers에는 양쪽 언어를 넣는다 |

## 4. 저작 프롬프트 (정본)

메인테이너가 자기 에이전트에 붙여넣는 블록. `agent-guide init`이 없어도 이것만으로 성립해야 한다.

````markdown
```
이 저장소의 AGENT_GUIDE.md를 작성하세요. Agent Guide v0.1 저작 프로토콜을 따릅니다.
규격: https://raw.githubusercontent.com/Open330/agent-guide/main/SPEC.md

【중요】이것은 README 요약본이 아닙니다. 사용자가 실제로 던지는 질문과
그 답이 있는 위치를 잇는 라우팅 테이블입니다.

1. 수집 — 파일 열람 15회 이내. 소스 파일 본문은 읽지 마세요.
   README 제목 목록 / 패키지 매니페스트 / docs 트리의 파일명과 첫 제목 /
   AGENTS.md·CONTRIBUTING.md 존재 여부 / CHANGELOG 최신 breaking change /
   최상위 소스 디렉터리 이름
2. FAQ — 지어내지 말고 캐내세요. 우선순위:
   이슈의 question 라벨 → README의 Troubleshooting과 접힌 절 →
   CHANGELOG의 버그 설명 → 비교표
   질문은 사용자의 말로 씁니다. 문서 제목을 물음표로 바꾸지 마세요.
3. covers — 질문자가 칠 검색어. 에러 메시지 원문이 가장 좋습니다.
   문서 제목의 단어를 그대로 쓰지 마세요.
4. Flow — onboard는 항상 (default). 아래는 열거형이 아니라 흔한 사례이니,
   구분되는 사용자층이 따로 있으면 그 층을 위한 flow를 새로 만드세요. 나머지는 증거가 있을 때만:
   CHANGELOG에 breaking change → upgrade / 트러블슈팅 문서 → troubleshoot /
   CI·SDK·Action 성격 → integrate / CONTRIBUTING.md → contribute
   FAQ가 한 줄뿐인 flow는 만들지 마세요.
5. Tasks — 명령은 README 코드 블록에서 그대로 가져오세요.
   verify는 실제 존재하는 명령만. 확인 못 하면 그 Task를 만들지 마세요.
````

## 5. 갱신 프로토콜

매니페스트는 한 번 쓰고 끝나지 않는다. 다음 시점에 갱신한다.

| 시점 | 무엇을 |
| :--- | :--- |
| breaking change를 담은 릴리스 | `upgrade` flow를 추가하거나 교체 |
| 세션 노트에 "답 못 함"이 쌓임 | 그 질문을 FAQ에 추가. **가장 값진 신호** |
| `validate`가 경로 깨짐을 보고 | Docs 표의 경로 수정 |
| 문서 대규모 개편 | Docs 표 재작성. covers는 유지 |

`.guide/session-notes.md`에 쌓인 미응답 질문 목록을 그대로 저작 프롬프트에 넣어 "이 질문들에 답할 수 있게 매니페스트를 보강해줘"라고 시키는 것이 갱신의 표준 경로다.
